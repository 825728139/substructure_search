## 补充复核：局部损坏的隔离

本次又确认并修复两类问题：

- **非法 JSONL 行阻断读取或被静默接受。** 数组/字符串行进入适配器后调用 `.get()` 导致未捕获异常；布尔值、零和字典形式的材料数组，又因 `or []` 被当作正常空数组。现在入口明确要求记录为对象、材料为数组、详情为对象；可选缺失和 `null` 仍按原约定接受，坏行记录为 `invalid_record`，后续好行继续读取。
- **单个损坏任务阻止整个服务启动。** 重启恢复原先逐个读取全部状态但不隔离数据错误，损坏 JSON、错配身份、坏快照或无关子目录都可能中断启动。现在只处理合法任务目录，无法读取的状态单独记录；有效状态若快照损坏则仍标记中断，并明确 `snapshot_unavailable`。坏文件保持原样，其他任务正常恢复。

新增诊断位于 `FileRunStore.recovery_issues`，`GET /health/ready` 在来源就绪时返回这些问题，只包含任务 ID、问题代码和异常类型。服务可以继续处理其他任务；这不表示损坏文件已被自动修复。真实权限/文件 I/O 错误继续阻止启动，避免把存储故障误判为单条坏数据。

验证见 [test_recovery_isolation.py](../tests/test_recovery_isolation.py)：先执行的 19 个场景修复前 13 个失败、6 个原有正例通过；随后补充健康接口诊断和真实 I/O 错误反例，共新增 21 项回归。完整项目 **188 项测试通过、无跳过**，静态、中文说明、契约及构建检查通过，固定样本评测使用当前实现哈希重跑。

## 补充复核：引用与诊断位置保留（2026-10-30）

在 `90325f9` 基础上检查结果、摘要与来源的对应关系，确认并修复三类追溯错误：

1. **生成结论时丢失已有引用。** 产品观察已有精确 `source_location`，结论却只复制整条记录的粗定位；审核文件提供的底物引用也未写入使用结论，进入模型摘要后只剩使用标志。现在产品结论的 `source.location` 保留该观察的具体位置，其他来源身份保持一致；输入结论按材料实例 ID 原样复制已有引用至 `evidence_text`。原来源记录不被改写，缺失/未知格式/属于其他材料的引用不补造。
2. **局部审核清空未修改的输入引用。** 只补充产品观察或另一个底物时，代码会用本次空/部分输入字典替换旧字典，但旧材料的使用标志仍然保留，造成事实与依据脱节。现在按材料 ID 合并引用，仅覆盖明确提供的项；空映射不撤销既有使用事实或引用。审核人、日期与补丁哈希仍描述本次更新。
3. **JSONL 错误行号偏移。** 先过滤空白行、再编号，导致文件第 4 行的错误被报告为第 2 行。现在过滤时同时保留原物理行号；记录额度仍按非空行计数，不因空白行改变导入上限。
