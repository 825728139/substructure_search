# 执行层代码审查

本轮只检查现有实现的执行逻辑、并发和异常路径，没有增加化学规则。审查覆盖任务接纳与幂等、排队取消、计算进程通信、截止时间、关闭、同步重排、文件原子写、快照标识和应用生命周期。

## 已确认并修复的问题

| 问题 | 影响与复现 | 修复 |
|---|---|---|
| 1. 半包消息阻塞硬超时，启动耗时未计入预算 | 原进程队列的 `get(timeout=...)` 在消息头可读后会继续阻塞读正文。测试子进程只发送消息头和少量正文，原有 2 秒预算超过 8 秒仍未结束。截止时间还在 `process.start()` 返回后才开始计算 | 改用单向管道，由独立接收线程读取完整消息，监督循环只从有界内存队列取已完成消息；截止时间从启动准备开始计算。正常大消息与子进程退出单独验证 |
| 2. 提交失败留下永久排队任务 | 幂等绑定写入或线程池调度失败后，任务状态仍是 `queued`，取消登记也未清理；幂等重试可能一直返回这个无人执行的任务 | 接纳失败统一标记 `failed`、清理内存登记并保留原始异常；已成功写入的幂等绑定指向真实失败状态 |
| 3. 排队取消未立即取消 Future | 唯一执行线程被占用时，取消第二个任务仅设置事件，仍占接纳名额并等待前项完成 | 排队 Future 直接取消，完成回调保存 `cancelled` 终态、释放名额；已有等待者也返回终态而非泄漏 `CancelledError` |
| 4. SDK 等待存在隐藏 130 秒上限 | 计算预算不包含排队，但 SDK 默认最多等待 130 秒；合法长队列会在任务仍可正常执行时抛出等待超时 | 默认等待包含排队，计算截止继续由监督器负责；显式 `wait(timeout=...)` 仍限制本次等待 |
| 5. 启动异常遗漏通信/进程资源清理 | 配置生成或 `process.start()` 在原清理区间之前失败，已分配资源无法保证关闭 | 将配置、启动与接收线程启动纳入统一 `try/finally`，分别关闭写端、接收端和已结束进程句柄；进程收尾异常也执行通信收尾 |
| 6. 原子写失败遗留临时文件 | `fsync` 或 `replace` 失败会留下完整或部分 `.tmp` 文件，重复失败持续占磁盘 | `finally` 尽力删除未发布的临时文件，同时保留旧目标文件和原始错误；文件读写显式使用 UTF-8 |
| 7. 快照 ID 读写校验不一致 | 写入没有 ID 校验；读取允许空 ID 或超长十六进制，后者直接引发文件名长度异常 | 读写共用标识校验：非空、小写十六进制、最长 64 字符，在文件系统调用前拒绝非法值 |
| 8. 关闭与同步重排不协调 | 已关闭客户端仍可写重排结果；关闭还可能在另一线程重排落盘前释放目录锁，让新协调器与旧客户端同时写 | 同步写操作登记活动计数；关闭先禁止新操作，等待已登记操作结束再释放目录锁。计算期间不持有全局协调锁，因此不阻塞其他任务取消；关闭后幂等命中也不能绕过检查 |
| 9. 应用生命周期异常跳过清理 | `lifespan` 在 `yield` 处抛异常时，后续关闭代码不会执行；取消作用域也可能取消清理等待 | 关闭放入 `finally` 并使用屏蔽取消的清理作用域，异常/取消退出都释放任务和目录锁 |

## 现在的执行路径

`RunManager.submit` 保存任务并提交监督线程；监督线程启动 `_worker`，拥有取消和截止时间判断。子进程通过单向管道发送完整阶段/最终资料；父进程 `_receive_packages` 线程接收完整消息，再放入最多一项的本地队列。这样消息传输半包不会阻塞监督循环，也不会无限积累阶段包。

正常结束、超时、取消和接收失败都会清理子进程与管道，再由父进程统一保存终态。排队任务无需启动子进程便可取消。同步重排通过 `active_writer` 登记，关闭等待它完成，排序计算时不占用协调锁。

## 边界

这里的硬预算控制计算子进程与消息接收，不是磁盘、操作系统故障下的严格实时保证。父进程的文件同步仍可能受异常存储设备影响；彻底不可写时，不能保证同时写出一个新的失败状态。进程、接收线程的收尾等待最多约 3 秒，另有实际存储 I/O 时间。

本轮没有修改或连接真实反应来源，也没有进行容器部署或千万级索引性能验收。以上结论来自代码审查、受控故障注入和本地回归。

## 补充复核：请求隔离与结果到达竞态

后续复核新增确认并修复两类问题，没有改变化学规则：

1. **共享可变对象使执行记录不一致。** Pydantic 的冻结配置不冻结内部列表。提交后修改原请求或返回状态中的排除材料列表，会影响后台执行，却不改变已经保存的请求；重排请求也有相同问题。外部传入的 `Settings` 可变，又可能改变客户端后续任务的来源配置。现在客户端复制配置；检索/重排接纳时序列化并重校验请求；返回的初始状态也与后台执行对象隔离。
2. **结果在中断之后到达仍被标记成功。** 监督循环只在等待消息之前检查取消和时间，若等待期间触及截止或收到取消，随后返回的最终包会直接标为成功。现在完整消息取出后再次检查取消与截止，再决定是否处理结果。

[test_request_races.py](../tests/test_request_races.py)中的 6 个场景修复前全部失败，修复后全部通过；分别覆盖原请求、返回状态、配置、重排请求的外部修改，以及结果接收期间的超时和取消。完整项目检查增至 **167 项测试通过、无跳过**，静态检查、中文说明、契约漂移及构建也通过。固定样本评测按当前实现哈希重新执行。

## 补充复核：预览副作用与 HTTP 配置隔离

本次继续审查现有代码，确认并修复两类接口问题：

1. **CLI 预览意外接管运行目录。** 原 `preview` 命令创建完整客户端，服务正在使用该目录时会因协调锁失败；服务停止且存在未完成任务时，仅预览一个分子也会触发恢复，把遗留任务改为失败。现在 `Client.preview(request)` 是无需客户端实例的静态方法，命令行直接调用，仍使用同一个查询规划器；已有实例调用方式也兼容。预览不创建协调器、不读取来源、不改变任务状态。
2. **HTTP 层仍保留外部可变配置。** 协调器已有配置副本，但 API 认证与就绪探测仍引用传入对象。应用创建后，外部清空 `api_token` 会关闭认证；修改来源路径会让就绪探测检查与任务执行不同的来源。现在 API 创建时也复制配置，应用配置保持创建时的值；更改部署配置后应重新创建应用。

## 补充复核：结果范围标记（2026-10-30）

1. **输入使用检索误报完成。** `usage_lookup` 原来只检查是否尝试过、检索循环是否结束以及全局停止原因。对称映射被截断、来源声明范围不完整、脏记录被隔离或详情读取失败时，可能没有全局停止原因，因而显示 `completed`，与资料包中的部分范围矛盾。现在同时检查输入通道各家族累积的完整性和来源问题。来源问题尚不能限定到某个角色时，保守保留 `partial`；没有尝试过或未请求时仍分别返回 `not_evaluated`、`not_requested`。

## 补充复核：关闭取消竞态与幂等恢复（2026-10-30）

在 `36e39d9` 基础上继续检查并发关闭和持久化异常路径，确认并修复两类问题：

1. **关闭取消后，等待者仍拿到排队状态。** `ThreadPoolExecutor.shutdown(cancel_futures=True)` 取消排队 Future 时，先唤醒等待者，再调用完成回调。回调尚未保存终态的窗口内，`RunManager.wait()` 捕获取消异常后直接读取磁盘，会返回旧的 `queued`。现在等待路径使用已有幂等 `_finish` 确认并保存 `cancelled` 再返回；稍后的回调不会重复改写终态。分别验证先等待后关闭、先关闭后等待两种时序，修复前均失败。
2. **损坏的幂等绑定可能导致重复任务。** 幂等文件中 `run_id` 为 null 或空值时，读取会返回假值，提交入口误认为没有旧绑定而接纳新任务；JSON 类型错误还会泄漏解析/类型异常。现在读取绑定时校验对象、请求摘要及合法任务编号，损坏统一返回 `RevisionConflict`（HTTP 409），保留原文件供检查，不覆盖坏绑定或重复创建任务。其他键仍正常使用，真实文件 I/O 错误继续向上传播。

新增 13 项测试：关闭竞态 2 项、损坏绑定及 API 不重复接纳 9 项、12 个线程同时提交同一幂等键的正常/冲突请求 2 项。11 项故障反例在修复前全部失败；并发对照确认相同请求均指向同一个任务，不同请求明确冲突，磁盘上只创建一个任务目录。测试入口为 [test_request_races.py](../tests/test_request_races.py) 和 [test_recovery_isolation.py](../tests/test_recovery_isolation.py)。

完整检查 **244 项测试通过、无跳过**，含真实 PostgreSQL 与 Chromium 集成，静态检查、中文说明、契约检查和 wheel 构建均通过。24 项固定样本评测按当前实现哈希重跑，结构命中与屏蔽隔离检查保持通过。这些结果验证所列场景，不等同于证明所有并发时序或存储故障已穷尽。
